## Architecture rules

The site is static, so anyone can call the database with the public key. The browser must never be trusted. These rules exist to stop cheating and to protect the ledger:

1. Every operation that changes marcones runs in a single Postgres function, in one transaction, with row locks. The browser has no direct write access to any game table.
2. Row Level Security is on for every table. Nothing is readable without a login.
3. The ledger is append-only, and each row stores the balance after it. A database constraint stops balances going below 0.
4. Roulette results and game outcomes are decided on the server with a secure random source. The browser only animates the result it receives.
5. Secret choices can't be read by anyone, including through the API or Realtime, until they're revealed.
6. Actions that need privileged Auth access (creating, removing and resetting users) run in Edge Functions, with the secret key stored only in Supabase.
7. Public sign-ups are disabled, because otherwise anyone with the public key could register.
8. Access tokens stay valid until they expire, so every function and policy must also check that the user is still active. Removal must take effect immediately.
9. Mobile networks retry and people double-tap, so every money action must be safe to submit twice (use a client request ID).
10. Each event stores a copy of its game settings when created, so later admin changes can't alter a running game.

## Rules

**Admin** (also a normal player) can:

- Create users (username + password) and remove them. Removal is a soft delete: the user can't log in, sessions are revoked, they leave the ranking, and their history stays in the audit. Block removal while they've accepted an open event.
- Add or remove marcones for any user with a required "Concept". A removal can't take a balance below 0.
- Reset a user's password, and cancel any open event (full refunds).
- New users start with 0 marcones. Usernames: lowercase `[a-z0-9_-]`, 3 to 20 characters.
- Configure the games and roulette easily from an admin screen.

**Every user, including the admin,** can:

- Create a classic event: name, buy-in, invitees (picked from existing users), and payout percentages for 1st, 2nd and 3rd (must sum to 100; a place may be 0%). The creator is automatically a participant and pays the buy-in on creation.
- Accept or decline invitations. Accepting charges the buy-in immediately, and is blocked if their balance is too low.
- Event states: open, then completed or cancelled. The creator can cancel while open (everyone is refunded). Participants can't withdraw after paying.
- The creator completes a classic event once at least 2 people have accepted. Pot = buy-in × accepted participants.
  - Exactly 2 participants: no ranking, the creator picks the winner, who takes the whole pot.
  - 3 or more: the creator picks distinct participants for each place with a percentage above 0, and the pot is split by percentage. Round each share down and give the remainder to the first paid place, so the total equals the pot exactly.
- See the **Ranking** (active users, balance, sorted descending).
- See a **user detail page** (tap anyone in the ranking for their balance and every movement involving them).
- See the **Audit** (global timeline, newest first, filterable by user: who, amount, concept or event, balance after, timestamp). It includes admin adjustments with their Concept, roulette spins and game payouts.

### Clarified edge cases

Treat these as settled unless they conflict with something else:

- The creator counts as an accepted participant. "Exactly 2 participants" means the creator plus one.
- Amounts are whole numbers. The minimum buy-in is 1. The creator needs enough balance, and must invite at least one person.
- Pending invitations lapse when an event completes or is cancelled. Removing a user declines their pending invitations.
- There's one admin: me. The admin can't remove themselves.
- Removed usernames can't be reused, so the audit stays unambiguous.
- Only the admin can change a password. A reset ends that user's sessions.
- Ranking ties are ordered alphabetically.
- Passwords must meet Supabase's minimum length.

## Games

Games are a type of event, chosen when creating one. The creator sets the buy-in, the admin sets the game's rules, and winners aren't picked by hand.

The inspiration is the hidden choices and betrayal of the indie game Another Door, but these must be **original games**. Don't reuse its names, art or text. The event detail screen must explain each game in full: its rules, its payoffs, who has locked in, and, after the reveal, every choice and payout. Before the reveal it must never hint at anyone's choice.

The two games share one engine: join, pay, lock in a secret choice, reveal automatically once everyone has chosen, pay out. A choice can't be changed once locked in. If someone never chooses, the creator or admin cancels the event, with full refunds.

**Admin game settings:** turn each game on or off, edit its Catalan description and numbers, and see a worked example update as the numbers change. Validate the settings. Changes affect new events only.

### Confia o traeix

A duel for exactly two players, based on the prisoner's dilemma. The creator invites one opponent. If they decline, the event is cancelled and the creator is refunded. Each secretly chooses **Confia** or **Traeix**. Payouts are a percentage of the buy-in, rounded down:

| Outcome | Default payout |
|---|---|
| Both trust | Each gets 150% |
| One betrays | The betrayer gets 250%, the other 0% |
| Both betray | Each gets 50% |

Validation: betrayer > both trust > both betray ≥ betrayed. The house covers or keeps any difference, shown in the ledger as normal movements.

### La minoria

A group game for 3 or more players. The creator starts it once at least 3 have accepted, and pending invitations lapse at that point. Each player secretly picks one of two options (default labels: **Cara** and **Creu**, editable by the admin). The smaller side splits the whole pot equally, rounded down, with the remainder going to whoever on that side locked in first. If the sides tie, or everyone picks the same option, everyone is refunded.

## Roulette

A red, black and white roulette, available from its own tab.

- Choose red or black and a bet. A win doubles the bet. White always loses.
- Default odds match real European roulette: red 18 in 37, black 18 in 37, white 1 in 37 (about 2.7%).
- Bets are whole numbers. The minimum is 1, and the maximum is 5% of the player's current balance, rounded down. The maximum is never below 1, so anyone with at least 1 marcona can still bet. The screen shows the current maximum, and the server enforces it.
- The admin can change the white chance and the maximum bet percentage, and turn roulette off.
- Each spin is a single ledger movement, showing the choice and the result in the audit.
- It needs a satisfying wheel or chip animation, which must also respect `prefers-reduced-motion`.
